Forms & input

Forms are where people act, not only read. An error reported at the wrong moment, or a format that forces retyping, increases abandonment. The six patterns below help people complete forms faster and with fewer errors. Every demo accepts real input and works with the keyboard.

Inline validation

Reports errors at the field, at the right moment. Instead of waiting for submit and then listing every error, the form checks each field when the user leaves it and removes the message as soon as the value is valid. The two forms in the demo are identical except for when they report errors. Type an email without “@” and press Tab in both forms, then try the username “alexm”, which is already taken.

Use whena field has clear rules that people often get wrong: email, a username that may be taken, a promo code, a phone number. Report the error on blur. Once an error is shown, re-check on every keystroke so the message clears as soon as the value is fixed.

Avoid whenthe check fires from the first character (“invalid email” after typing “a”), or an empty field turns red only because the user tabbed past it. Still validate on submit and move focus to the first invalid field.

Prompt tip: state the timing (“validate on blur, re-validate on input once an error is shown”). Without it, AI tools usually validate on every keystroke.

Multi-step form / Wizard

Splits a long form into steps. Each screen asks a few related questions, a progress indicator shows how many steps remain, and users can go back and edit without losing what they entered. The last step shows every answer for review before submitting. Fill in the form, then select “Back” or a completed step name to move between steps.

Use whenthe form has more than 6–8 fields that fall into meaningful groups (account → details → payment): sign-up, onboarding, checkout, job applications. Short steps reduce cognitive load, and answers from earlier steps can prefill later ones.

Avoid whenthe form has only 3–5 fields (steps only add clicks), or users need to see all fields at once to compare them. Do not ship a wizard without a Back button, or one that loses data when the user goes back.

Prompt tip: name the three requirements most often missed: “back button keeps entered data”, “review step with edit links”, “focus moves to step heading on change”.

Autocomplete / Combobox

A text input with a list of suggestions. As the user types, the list narrows to matching items; the user chooses one with a pointer, touch, or ↑ ↓ Enter. Matching ignores case, accents and spaces, so “sao paulo”, “saopaulo” and “São Paulo” return the same result. Type “zurich”, “saigon” or “san”, then choose a result with the keyboard.

    Typed…Matched as…
    ↓ ↑Move through suggestionsEnterChoose the highlighted suggestionEscClose the list; press again to clearAlt ↓Open the list when the field is empty

    Use whenthe user picks one item from a long list (cities, countries, products, team members) and already knows what they want: typing three characters is faster than scrolling a 60-option <select>.

    Avoid whenthere are fewer than 7 options (use radio buttons or a select), or users do not yet know what the options are (let them browse a list). Do not overwrite the text the user is typing, and do not require exact accents or capitalization for a match.

    Prompt tip: ask for “accent- and case-insensitive matching (normalize NFD, strip combining marks)” and the “WAI-ARIA combobox pattern”. Without them, AI tools often build a list of divs that does not work with the keyboard.

    Date picker

    Picks a date from a month calendar. The date field accepts typed input (MM/DD/YYYY) and has a button that opens a month view, which marks today and disables dates that cannot be chosen. Next to it (below it on mobile) is the browser’s native date input for comparison. Select the calendar icon, then choose a date by tapping or with the arrow keys, Page Up, Page Down, Enter and Esc.

    Type MM/DD/YYYY or choose from the calendar

    SuMoTuWeThFrSa
    Past dates unavailable

    The native equivalent

    <input type="date">: the browser draws the calendar and provides keyboard and screen reader support without any JavaScript. In exchange, its appearance and date format vary by browser, operating system and system language.

    Use whenthe date is close to today and the day of the week matters: appointments, bookings, deadlines, date ranges. A calendar shows “next Saturday” at a glance, without mental arithmetic.

    Avoid whenthe date is far away and already known, such as a date of birth: going back 30 years in a calendar takes many steps, and three separate fields or a typed date are faster. Always allow typing alongside the calendar.

    Prompt tip: state the locale, for example “week starts on Sunday, en-US, MM/DD/YYYY” or “week starts on Monday, en-GB, DD/MM/YYYY”, and “keyboard: arrows, PageUp/PageDown, Home/End, Esc returns focus”. Without a locale, AI tools default to one that may not match your users.

    Password strength meter

    Rates password strength as the user types. A four-segment bar changes color on each keystroke, with one specific suggestion for a stronger password and a checklist that updates itself. Length matters more than special characters. Enter “password123”, then a long passphrase such as “correct horse battery staple”.

    Use whenusers create their own password: sign-up, password change, password reset. Feedback on each keystroke lets them adjust the password before the form rejects it.

    Avoid whenthe field is for signing in (users enter an existing password, so there is nothing to rate). Do not score by rules such as “contains a symbol means strong”: “P@ssw0rd” is cracked in seconds. Block common passwords and reward length instead.

    Prompt tip: write “zxcvbn-style scoring, reward length, block common passwords” and “show / hide password toggle” so the meter does not only count special characters.

    Input mask

    Formats input as the user types. The user types digits only; the field inserts parentheses, spaces, hyphens or “/” in the right places and shows the rest of the format in light gray. The submitted value is still the unformatted digit string. Type a number, edit a digit in the middle, delete across a separator, or paste “+1 (555) 123-4567”.

    Submitted value

    tel
    cc-number
    cc-exp

    Test card number: 4111 1111 1111 1111 (passes the Luhn check). The mask only changes the display; the server receives and validates the unformatted digits.

    Use whenthe data has a fixed format and grouping helps proofreading: phone numbers, card numbers, expiry dates, tax IDs, account numbers. Groups of 4 digits are easier to check than 16 digits in a row.

    Avoid whenthe data has no fixed format (names, addresses, international phone numbers of varying length). A mask that moves the caret, blocks paste or prevents deleting across separators does more harm than no mask.

    Prompt tip: ask for “preserve caret position when editing in the middle”, “backspace across separators” and “accept pasted values with spaces, parentheses or +1”. These are the three points where hand-written masks most often fail.
